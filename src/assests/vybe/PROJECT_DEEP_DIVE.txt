================================================================================
SECTION 1 — 30-SECOND PROJECT PITCH
================================================================================

VYBE is a real-time, full-stack social music streaming platform built using React 18, TypeScript, Node.js, Express, MongoDB, Socket.IO, Clerk, and Cloudinary. It combines direct Creative Commons music streaming via the Jamendo API with global mainstream music metadata discovery (Spotify & MusicBrainz Web APIs). It features real-time 1-on-1 messaging, live user presence and listening activity broadcasting, synchronized LRC lyrics parsing, mood-based recommendation feeds, personal playlist management, and a Clerk-authenticated admin management dashboard.

================================================================================
SECTION 2 — 2-MINUTE PROJECT EXPLANATION
================================================================================

VYBE was engineered to solve three major challenges in modern web music applications:
1. Legal Audio Streaming vs. Global Metadata Search: Streaming licensed audio is costly. VYBE integrates with the Jamendo API to stream legal, open-access Creative Commons audio directly, while using Spotify Web API (Client Credentials Flow) and MusicBrainz to provide rich metadata discovery for mainstream artists, tracks, and albums worldwide.
2. Real-Time Social Listening & Chat: VYBE implements WebSockets using Socket.IO. As users play tracks, state updates are broadcast in real-time across connected clients (`update_activity`, `live_activity_state`), rendering live soundwave equalizer animations and allowing friends to "listen along" or send tracks in 1-on-1 private chat sessions.
3. Progressive Auth-Aware Architecture: Using `@clerk/express` on the backend and `@clerk/clerk-react` on the frontend, VYBE maintains a single authoritative authentication state. Non-logged-in guest users can browse, search, and stream public tracks, but attempts to perform personal actions (Liking songs, saving playlists, messaging) trigger modal prompts (`AuthModal`) or route gates (`AuthGate`), maintaining clean security without breaking playback.

================================================================================
SECTION 3 — WHY I BUILT IT
================================================================================

I built VYBE to demonstrate how to architect a modern, reactive media application combining RESTful micro-services, real-time WebSocket state synchronization, multi-provider API fallback chains, and clean role-based user management. The goal was to build a polished, production-grade application that balances audio playback engine state, progressive authentication gating, and synchronized media presentation (lyrics and soundwaves) in a single-page React application.

SECTION 4 — COMPLETE USER FLOW
================================================================================

4.1 GUEST USER FLOW
--------------------------------------------------------------------------------
1. Entry: Guest lands on `/` (Home Page).
2. Navigation: Guest can navigate to `/explore`, `/vibes`, `/search`, and `/jamendo`.
3. Discovery & Playback: Guest selects a mood tag under "What's Your Vybe?" or searches for a track. Click Play initializes `usePlayerStore` queue and streams audio.
4. Protected Action Trigger: Guest clicks Heart (Like) button in `PlaybackControls` or sidebar link `/library`.
5. Auth Gate Interception: Instead of a crash or raw 401 HTTP error:
   - Clicking Heart opens `AuthModal` ("SAVE YOUR VYBE").
   - Navigating to `/library` renders `AuthGate` component with Clerk `[ Log in ]` / `[ Sign up ]` options.
6. Authentication: Guest clicks `Log in` or `Sign up`, completing Clerk authentication.

4.2 AUTHENTICATED USER FLOW
--------------------------------------------------------------------------------
1. Authentication Callback: User logs in via Clerk SSO/OAuth. Clerk redirects to `/auth-callback`. `AuthCallbackPage` sends POST `/api/auth/callback` to backend, syncing `clerkId`, `fullName`, and `imageUrl` to MongoDB `User` model.
2. Personalized Home: Redirects to `/`. `HeroSection` displays time-based greeting ("Good morning, Sneha ⚡").
3. Library Management: User creates custom playlists (`CreatePlaylistModal`), likes songs (creates `Like` document), and listens to tracks (logs `Recent` document).
4. Real-time Social Interaction: Socket.IO connects automatically (`user_connected`). Playing a song emits `update_activity` socket event, updating live sidebar indicators across all connected clients. User opens `/chat`, selects an online user, and sends a text or track share message.
5. Admin Capabilities (If Admin): If primary email matches `ADMIN_EMAIL`, `Admin Dashboard` button appears in `Topbar`. Admin visits `/admin`, uploads audio & cover art to Cloudinary, and manages database catalog.

SECTION 5 — SYSTEM ARCHITECTURE
================================================================================

VYBE follows a Monolithic SPA + REST API + WebSocket architecture:

```text
[ Browser / Single Page App ]
       │
       ├──── HTTP / REST Requests (Axios) ────► [ Express REST API (Port 4000) ]
       │                                                 │
       │                                                 ├──► Clerk Express Middleware (Auth)
       │                                                 ├──► MongoDB / Mongoose ODM (Data)
       │                                                 ├──► Cloudinary SDK (Media Uploads)
       │                                                 ├──► Jamendo API v3.0 (CC Audio)
       │                                                 ├──► Spotify Web API (Metadata)
       │                                                 ├──► MusicBrainz API (Fallback)
       │                                                 └──► LRCLIB API (LRC Lyrics)
       │
       └──── WebSockets (Socket.IO Engine) ────► [ Socket.IO Server (HTTP Server) ]
                                                         │
                                                         ├──► In-Memory UserSockets Map
                                                         ├──► In-Memory UserActivities Map
                                                         └──► MongoDB Message Collection
```

Architecture Designation: SPA + REST API + WebSocket Server (Integrated Node.js Monolith).

SECTION 6 — REQUEST / DATA FLOWS
================================================================================

6.1 UNIFIED SEARCH REQUEST FLOW
--------------------------------------------------------------------------------
User types "Blinding Lights" in Search Page input
   ↓
Frontend Component: `SearchPage.tsx`
   ↓
API Request: GET `/api/search?q=Blinding%20Lights&category=all&limit=12`
   ↓
Express Route: `search.route.js` -> `searchCatalog()` controller
   ↓
Service: `CatalogService.search()`
   ↓
Cache Check: Checks in-memory `CatalogService.cache` Map (`search:blinding lights:all:12`). If valid (< 5 min), return cached response.
   ↓
Parallel Provider Fetch (Promise.all):
   ├── JamendoService.getDiscoverTracks() -> GET https://api.jamendo.com/v3.0/tracks/?client_id=...&namesearch=Blinding%20Lights
   └── SpotifyService.search() -> GET https://api.spotify.com/v1/search?q=Blinding%20Lights (with Client Credentials token)
   ↓
Fallbacks (If Spotify fails/empty): `MusicBrainzService.search()` -> GET https://musicbrainz.org/ws/2/recording/
   ↓
Relevance Ranking: `CatalogService.rankTracks()` ranks results using string matching scoring (Exact title+artist = 100pts, Exact title = 80pts, etc.). Playable Jamendo tracks flagged `isPlayable: true`; Spotify tracks flagged `isPlayable: false`.
   ↓
HTTP 200 Response: JSON containing `{ playable: [...], external: { tracks: [...], albums: [...], artists: [...] } }`
   ↓
Frontend Update: `useSearchStore` updates state; UI renders Playable cards and External discovery cards.

6.2 REAL-TIME CHAT & ACTIVITY BROADCAST FLOW
--------------------------------------------------------------------------------
User plays a song in `usePlayerStore` (`setCurrentSong(song)`)
   ↓
`broadcastActivity(song, true)` called in `usePlayerStore`
   ↓
Socket Event: `socket.emit("update_activity", { userId, isPlaying: true, track: song, activity: "Playing..." })`
   ↓
Backend Socket Server (`socket.js`): Handler updates internal `userActivities` Map.
   ↓
Broadcast: `io.emit("activity_updated", ...)` and `io.emit("live_activity_state", ...)`
   ↓
All Connected Clients: `useChatStore` socket listener updates `liveActivities` Map.
   ↓
UI Update: `FriendsActivity.tsx` renders live soundwave equalizer animation and "Listen Along" button on target user's avatar.

6.3 ADMIN SONG CREATION FLOW
--------------------------------------------------------------------------------
Admin submits new song form with audio file (.mp3) and image file (.png)
   ↓
Frontend: POST `/api/admin/songs` with FormData payload and Auth Bearer Header
   ↓
Route & Middleware: `admin.route.js` -> `protectRoute` -> `requireAdmin` (verifies Clerk email against process.env.ADMIN_EMAIL)
   ↓
Express FileUpload: Intercepts files into temporary local directory `tmp/`
   ↓
Controller: `admin.controller.js` -> `createSong()`
   ↓
Cloudinary Upload: `uploadToCloudinary(audioFile)` and `uploadToCloudinary(imageFile)` uploads files from `tmp/` to Cloudinary bucket.
   ↓
Database Operation: `Song.create({ title, artist, audioUrl, imageUrl, duration, albumId })` created in MongoDB. If `albumId` present, `Album.findByIdAndUpdate($push: { songs: song._id })`.
   ↓
HTTP 201 Response: Returns created `Song` JSON object.

SECTION 7 — FEATURE-BY-FEATURE INTERNAL WORKING
================================================================================

7.1 AUDIO PLAYBACK ENGINE (`usePlayerStore.ts` & `PlaybackControls.tsx`)
- Audio HTML Element: Managed via HTML5 `<audio>` element reference.
- State: Tracks `currentSong`, `isPlaying`, `queue`, `currentIndex`, `volume`, `isMuted`, `shuffle`, `repeat` ("none" | "all" | "one"), `currentTime`, `duration`.
- Playable Guard: `setCurrentSong` checks `song.isPlayable !== false && song.type !== "external"`. If external, opens track's `externalUrl` in a new browser tab without cluttering audio player state.

7.2 MOOD DISCOVERY ENGINE ("What's Your Vybe?") (`vibes.ts` & `VibesPage.tsx`)
- Mood Configurations: 8 pre-configured vibe profiles (*Energy Boost*, *Chill Mode*, *Focus Flow*, *Late Night*, *Party Vibes*, *Melancholy*, *Road Trip*, *Feel Good*).
- Dynamic Querying: Requests GET `/api/jamendo/discover?tag={vibeTag}&limit=24&offset={offset}`.
- Pagination / Refresh: "Refresh Vibe" increments offset by 20 to fetch fresh recommendations.

7.3 SYNCHRONIZED LRC LYRICS READER (`lyrics.service.js` & `LyricsPage.tsx`)
- LRC Parser: `parseLRC()` processes raw LRC strings containing timestamps like `[MM:SS.xx]` into structured arrays `[{ start: number, text: string }]`.
- Multi-Source Resolution:
  1. For Jamendo tracks: Queries Jamendo Lyrics API (`/v3.0/tracks/lyrics/`).
  2. Fallback: Queries LRCLIB API (`https://lrclib.net/api/get` or `/search?q=...`).
- Synchronized Highlighting: `LyricsPage.tsx` listens to player `currentTime` and highlights active lyrics line matching `start <= currentTime`.

SECTION 10 — AUTHENTICATION & AUTHORIZATION
================================================================================

1. Client Auth State: Handled via `@clerk/clerk-react`. `useUser()` provides `user` and `isSignedIn`.
2. Request Attachment: `AuthProvider.tsx` fetches Clerk JWT token (`getToken()`) and attaches `Authorization: Bearer <token>` to Axios headers.
3. Backend Validation: `express` application uses `clerkMiddleware()` from `@clerk/express`, populating `req.auth` on incoming HTTP requests.
4. Route Protection (`auth.middleware.js`):
   - `protectRoute`: Checks `if (!req.auth.userId) return res.status(401)`.
   - `requireAdmin`: Fetches Clerk user details via `clerkClient.users.getUser(req.auth.userId)` and verifies `process.env.ADMIN_EMAIL === primaryEmail`. Returns 403 if invalid.
5. Frontend Route Protection (`ProtectedRoute.tsx` & `AuthGate.tsx`): Route gate wrapper checks `isSignedIn`. Unauthenticated requests render `<AuthGate>` component rather than failing silently.

SECTION 12 — HARDEST ENGINEERING PROBLEMS
================================================================================

PROBLEM 1: UNIFIED SEARCH & PLAYABLE VS EXTERNAL TRACK DISTINCTION
- Problem: Searching mainstream songs return copyrighted tracks that cannot legally be streamed directly via custom HTML5 audio tags without violating licensing.
- Root Cause: Mainstream APIs (Spotify Web API) provide track metadata but strictly prohibit direct MP3 stream extraction.
- Implementation: Built `CatalogService.js` to query Jamendo (for playable CC MP3 streams) and Spotify/MusicBrainz (for discovery metadata) in parallel. Standardized songs into unified schemas with explicit flags: `isPlayable: true | false` and `type: "playable" | "external"`.
- Trade-off: Mainstream tracks cannot be played inside the internal HTML5 audio player; clicking them redirects users to the official external track page or Spotify URL.

PROBLEM 2: REAL-TIME SOCKET ACTIVITY STATE SYNC
- Problem: Tracking live listening activities across multiple clients requires frequent socket broadcasts without overloading memory or emitting stale states.
- Root Cause: Network reconnections or rapid song switching could cause race conditions in user activity states.
- Implementation: Maintained an in-memory `userActivities` Map on the Socket.IO server keyed by `userId`. Emitted full state snapshots (`live_activity_state`) on new connection and differential updates (`activity_updated`) on track change.
- Trade-off: Server memory holds user activity state in RAM. Server restart resets active live activity snapshots until clients re-emit.

SECTION 13 — ENGINEERING DECISIONS
================================================================================

1. Monolithic Node.js + Express backend instead of Microservices: Chosen for simplicity and low latency when managing socket instances, DB models, and external service adapters in a unified codebase.
2. Zustand for Frontend State Management instead of Redux Toolkit: Zustand provides lightweight, un-opinionated store modules (`usePlayerStore`, `useMusicStore`, `useChatStore`) without boilerplate code.
3. Clerk for Auth instead of Custom JWT / Passport: Offloads OAuth security, session persistence, token refreshes, and multi-factor auth to a dedicated identity provider while remaining easily verifiable on the backend using `@clerk/express`.
4. Embedded Documents in Playlists & Likes Schemas: Storing song subdocument snapshots directly inside `Playlist` and `Like` documents avoids expensive multi-table joins when rendering user libraries.

SECTION 15 — ERROR & FAILURE SCENARIOS
================================================================================

1. Jamendo API Failure / Missing Credentials: `JamendoService` catches HTTP errors or missing `JAMENDO_CLIENT_ID` and seamlessly falls back to pre-configured CC sample tracks (`FALLBACK_TRACKS`), ensuring the UI never displays broken catalog components.
2. Spotify Credentials Missing: `SpotifyService` gracefully handles missing credentials by returning empty arrays or delegating to `MusicBrainzService` / static mainstream fallback catalog.
3. LRCLIB API Down: `LyricsService` returns `hasSynced: false` with fallback message `"No lyrics available for this track"`, preventing lyrics page crashes.
4. Database Disconnection: Express error handler middleware catches DB errors and returns 500 JSON response (`"Internal server error"` in production).

SECTION 20 — INTERVIEWER ATTACK MODE (Q&A)
================================================================================

Q1: Why did you choose MongoDB instead of PostgreSQL?
Strong Answer: MongoDB's flexible JSON document model allowed us to store embedded subdocuments for tracks inside Playlists and Likes without requiring multi-table SQL JOIN queries on every track render. This reduced read latency for user library views.

Q2: How do you handle non-playable mainstream songs in your player engine?
Strong Answer: In `usePlayerStore.ts`, `setCurrentSong` inspects the track's `isPlayable` flag and `type`. If `isPlayable === false` or `type === "external"`, the player engine guards itself and opens the track's external URL in a new tab instead of attempting to feed an unplayable URL to the HTML5 `<audio>` element.

Q3: How do you prevent unauthorized users from accessing admin routes?
Strong Answer: Defense in depth. On the backend, `requireAdmin` middleware inspects the primary email of the Clerk authenticated user against `process.env.ADMIN_EMAIL` and returns 403 Forbidden. On the frontend, `ProtectedRoute` checks both `isSignedIn` and `isAdmin`, hiding the admin dashboard button and gating the route.

Q4: What happens if the Jamendo or Spotify API fails during search?
Strong Answer: The application implements a multi-tiered fallback strategy. If Jamendo fails, it returns normalized static fallback tracks. If Spotify fails, it falls back to MusicBrainz API, and if MusicBrainz returns empty, it falls back to a curated static mainstream catalog array, ensuring the user experience remains uninterrupted.
